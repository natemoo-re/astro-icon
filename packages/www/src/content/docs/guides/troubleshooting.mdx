## An icon ignores CSS `color`

An icon's `fill`/`stroke` only responds to CSS `color` if the source SVG uses `currentColor` rather than a hardcoded color. Both icons below are styled with the exact same rule, `color: #e11d48` — only the one authored with `currentColor` picks it up:

<svg viewBox="0 0 24 24"><path fill="#64748b" d="..." /></svg>

<!-- Will -->

<svg viewBox="0 0 24 24"><path fill="currentColor" d="..." /></svg>`}>
  <figure style="margin:0;display:flex;flex-direction:column;align-items:center;gap:0.35rem">
    <svg width="32" height="32" viewBox="0 0 24 24" style="color:#e11d48" aria-hidden="true"><path fill="#64748b" d="M12 21.35 10.55 20C5.4 15.36 2 12.28 2 8.5 2 5.42 4.42 3 7.5 3c1.74 0 3.41.81 4.5 2.09C13.09 3.81 14.76 3 16.5 3 19.58 3 22 5.42 22 8.5c0 3.78-3.4 6.86-8.55 11.54Z"/></svg>
    <figcaption style="font-size:0.7rem;opacity:0.7">hardcoded fill</figcaption>
  </figure>
  <figure style="margin:0;display:flex;flex-direction:column;align-items:center;gap:0.35rem">
    <Icon name="mdi:heart" size={32} style="color:#e11d48" />

  </figure>

Most Iconify icon sets use `currentColor` already — their maintainers normalize each icon before publishing it. Local, hand-authored `.svg` files usually haven't been through that step.

### How Astro Icon warns you

`localIcons()` never rewrites a file's colors for you: only you can tell a deliberately-colored logo apart from a UI glyph that just hasn't been converted, and guessing wrong silently changes what ships.

What it does instead is warn. After each sync, if any icon looks like a single-color glyph that would benefit — no `currentColor` anywhere, and no more than one distinct explicit `fill`/`stroke` — it logs how many. Multi-color icons (two or more distinct explicit colors, read as a deliberate graphic) are never flagged.

### The fix

Edit the `.svg` file to use `currentColor`, or convert a whole collection at once with `svgo()`'s `convertColors` override:

```ts title="src/content.config.ts"
import { defineCollection } from "astro:content";
import { localIcons } from "astro-icon/loaders";
import { svgo, defaultOverrides } from "astro-icon/optimize";

export const collections = {
  icons: defineCollection({
    loader: localIcons("src/icons", {
      optimize: svgo({
        plugins: [
          {
            name: "preset-default",
            params: {
              overrides: {
                ...defaultOverrides,
                convertColors: { currentColor: true },
              },
            },
          },
        ],
      }),
    }),
  }),
};
```

## An icon ignores `stroke-width` or another presentation attribute

Passing a presentation attribute like `stroke-width`, `stroke-linecap`, or `fill` to `<Icon>` sets it on the rendered `<svg>`, and it cascades to every nested element that doesn't declare its own value — normal SVG inheritance, and it works for most icon sets.

It breaks down for sets (Tabler is a common example) that redundantly redeclare the same attributes on inner `<path>`/`<g>` elements. Once an element has its own value for a property, it never falls back to inheriting one from an ancestor, no matter what you pass:

```astro "stroke-width={3}"
<!-- The outer <svg> gets stroke-width="3", but nested elements keep their
     own redundant stroke-width from the source icon and ignore it. -->
<Icon name="tabler:rss" stroke-width={3} />
```

The fix belongs in the icon set's `optimize` step, not on every `<Icon>` usage: strip the redundant attribute from the inner markup so it's only set once, at the root, and can inherit normally. This applies to any presentation attribute redeclared this way — `stroke`, `stroke-width`, `stroke-linecap`, `stroke-linejoin`, `stroke-dasharray`, `fill`, and so on — for any icon source.

```ts title="src/content.config.ts" "optimize"
import { defineCollection } from "astro:content";
import { createIconLoader, iconifyLocalSource } from "astro-icon/loaders";

export const collections = {
  tabler: defineCollection({
    loader: createIconLoader(
      iconifyLocalSource("tabler", {
        optimize: (svg) => svg.replace(/\sstroke-width="2"(?=[\s/>])/g, ""),
      }),
    ),
  }),
};
```

## Autocomplete isn't showing my icons

`<Icon name="...">` autocompletes from a generated types file that doesn't exist until a sync has run. Check both:

1. `src/env.d.ts` references it:

   ```ts title="src/env.d.ts"
   /// <reference path="../.astro/astro-icon.d.ts" />
   ```

2. You've run `astro sync`, `astro dev`, or `astro build` at least once since defining the collection.

## Masks or gradients render inconsistently

Icons with internal `id` references (`<mask id="a">`, `url(#a)`) duplicate those ids when the same icon renders more than once without [automatic sprite optimization](/guides/sprite/), which can make them resolve against the wrong element. Prefix each icon's ids with its name — see [the `prefixIds` recipe](/guides/optimize/#prefixing-ids-to-avoid-collisions).

## Sprite optimization does nothing

Check that the `icon()` integration is added to `integrations` in `astro.config.mjs` — without it, every `<Icon>` renders as a plain, standalone `<svg>`, same as if no icon repeated. Also check the collection's loader wasn't configured with `sprite: false`, and that the specific usage doesn't pass the `inline` prop, which opts a single `<Icon>` out. See [“Automatic sprite optimization”](/guides/sprite/).
